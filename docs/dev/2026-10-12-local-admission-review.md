### POST R1

## FINDINGS

- **LA-POST-01 — WARN — Bounded batches cannot advance beyond their first 500 rows.** Location: `src/app/api/enrich/route.ts:48–51`, with the same ascending `take: 500` selection in `src/app/api/enrich/refresh/route.ts:24–33`, `src/app/api/enrich/metacritic/route.ts:20–23`, and `src/app/api/enrich/ai/route.ts:27–31`. Force enrichment selects every game on each request, so its next request always repeats the same first 500. Refresh/score jobs also retain rows for which the provider has no missing data, and unsuccessful metadata/AI rows can block later rows. The new cap therefore makes later library rows unreachable through the documented “Continue another batch” operation and can repeatedly consume provider budgets. An actual 501-game fixture executed two force requests: both enriched 500, both reported remaining/pending 1, both dispatched IDs 1–500, and ID 501 remained unenriched. **Minimal fix:** give each bounded pass a validated cursor/continuation contract and make its callers advance it until that pass is drained, including when early rows fail or remain incomplete.

- **LA-POST-02 — WARN — The new stop/optional-failure events are ignored by their real UI consumers.** Locations: `src/app/api/enrich/route.ts:95–107` and the corresponding AI/refresh/score stop emitters; `src/context/enrichment-context.tsx:194–207,228–236`; `src/components/enrichment-bar.tsx:18–37`; `src/app/api/discover/route.ts:267–274` → `src/app/(main)/discover/page.tsx:119–122`; `src/app/api/upload/process/route.ts:315–324` → `src/app/(main)/admin/upload/page.tsx:392–415`. EnrichmentContext ignores `type: "stopped"`, derives success only from `networkDown`, and fills current to total. Rendering the actual context and bar with the new stopped-budget SSE contract returned `success: true`, displayed green “Done” and `3/3` after only one processed item, and displayed no budget reason. Discover ignores its new `stopped` event, and Upload ignores `enrich-skipped` / `enrich-error` before displaying the successful transfer as done. This defeats the plan’s visible budget-stop and nonfatal-but-visible upload-enrichment contract. **Minimal fix:** update these consumers to retain and display stop/optional-enrichment reasons, preserve partial processed counts, and report unsuccessful main-operation completion while retaining successful transfers.

- **LA-POST-03 — WARN — Existing db-push installations have no supported migration path to the new startup contract.** Locations: `docker-entrypoint.sh:6`, `Dockerfile:47–49`, `README.md:118,129`. The previous runner executed `prisma db push`; the new runner unconditionally executes `prisma migrate deploy`. A nonempty SQLite schema initialized by db push has no migration history, and migrate deploy refuses it with P3005 before server startup. The README discusses existing mounts and says startup applies additive migrations, but gives no baseline/upgrade procedure or existing database-path transition. In an own migrated fixture, removing only migration history and the new admission tables to model the previous db-push schema made the exact new Prisma command exit 1 with P3005 / “database schema is not empty”. **Minimal fix:** provide a backed-up, schema-checked baseline/upgrade procedure for existing db-push databases, including preservation of the existing SQLite file and encryption key; keep migration errors fail-closed rather than restoring the old db-push fallback.
